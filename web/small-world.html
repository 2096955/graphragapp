Small-world graphs, and why two hops can reach most of the graph

A ring where everyone knows only their neighbours needs many hops to cross. Rewire a few edges at random and most nodes end up two or three hops from each other. Many real networks behave like this (Watts and Strogatz showed it for film actors, a power grid and a worm’s nervous system), and knowledge graphs with hub entities tend to as well. That changes how an agent should retrieve context.

What it means for agent context

Hop limits are not a budget

In a small world, "two hops" can mean most of the graph. Cap retrieval by tokens and rank what comes back (Lab 2 in the field guide), not by hop count alone.

Hubs are both shortcut and trap

A few high-degree nodes, such as a parent company, a shared service or a common regulation, make paths short. Expanding through one floods the context. Cap fan-out per node or down-weight hubs in ranking.

Clustering is what makes graphs useful

High clustering means a node's neighbours know each other, so one local neighbourhood is coherent context. A purely random graph (β = 1) loses that and behaves more like vector search.

Engine choice follows the shape

Short, wide traversals over small-world data suit engines built for many-to-many expansion: FalkorDB's sparse matrices and Kuzu's factorised execution. Deep chains suit pointer-following engines such as Neo4j.

The same model elsewhere

NetworkX's generator follows the same model but differs in detail (it skips a rewire rather than retrying when a node is already fully connected), so expect small differences in individual runs.

import networkx as nx

G = nx.watts_strogatz_graph(n=500, k=50, p=0.15, seed=1)  # NetworkX k = 2K
print(nx.average_shortest_path_length(G))  # excludes self-distances
print(nx.average_clustering(G))
// Neo4j or FalkorDB: load the downloaded CSV
LOAD CSV WITH HEADERS FROM 'file:///edges.csv' AS row
MERGE (a:Node {id: toInteger(row.source)})
MERGE (b:Node {id: toInteger(row.target)})
MERGE (a)-[:LINK]-(b);

// Reach in two hops from node 0
MATCH (n:Node {id: 0})-[:LINK*1..2]-(m)
RETURN count(DISTINCT m) AS reached;
