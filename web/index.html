Typed decisions for graph-based dataset discovery

Agents make many small calls: can this request be answered, which pollutants and breakdowns does it mean, should this payload go through. This lab puts a small typed decision model on each of those calls and uses a knowledge graph for everything else. Kuzu holds the graph. A typed decision model answers the fixed questions: Laya or AnyJev (open source, measured here), TypeSafe Jev (commercial API, supported but not measured here) or plain catalogue rules. A person reviews what the model is unsure about. The lab measures when that confidence can be trusted. For which graph database to build this on, open the field guide.

Why hop count does not bound context

In a small-world graph a few shortcuts make almost everything close. In this 500-node example, two hops from one node reach three quarters of the graph. An agent that expands k hops from a match fills its context long before k is interesting, so retrieval has to stop on a token budget or a ranking. The typed decisions below are one way to rank: they keep the candidates that matter and drop the rest. These figures are a synthetic example, not a measurement of the catalogue graph. Worked example: compliance filter

A legal and compliance agent sits in front of a research agent. A typed decision releases, redacts or blocks each payload: TypeSafe Jev, Laya or AnyJev, or the catalogue rules with no keys. It fails closed: a backend error blocks, and so does a "redact" with nothing the redactor can remove. Kuzu keeps a keyed pattern identity, the decision and the attempt count, not the payload, so a second attempt with the same address shows up as graph state. The identities are keyed hashes: pseudonymised, not anonymous. Arize, when configured, receives each decision as a trace. Whether a decision was right comes from 30 hand-labelled payloads, never from the rules themselves. This is a lab walkthrough, not a production filter: there is no retention policy, and 30 labels are a check, not a benchmark.

The pipeline

The discovery method from Diamantini et al. (2026). A decision model makes each call the request leaves open; where the request names something in catalogue terms, that is used and the model is checked against it. Low confidence or a disagreement sends the result to review. The graph proposes candidates and finds datasets; the model never writes text, and the explanation never makes a decision.

Decision model

Can the probabilities be trusted?

Each model answered the same 584 labelled decisions. A threshold such as "act above 0.9" only works if a stated 0.9 is right about 90 times in 100, so three things are measured: how often the model is right, how far its confidence is from its accuracy, and how much it could decide without a person at a target error. Decisions from one request are not independent, so intervals resample whole requests, and every held-out figure uses thresholds chosen on other requests than the ones it is scored on.

    Read the numbers with care. The catalogue and its eight sources are synthetic. Labels are hand-written against LABELLING.md in the repository and should be reviewed before anyone relies on them. The 584 decisions come from 62 requests, 8 sources and 82 name pairs, so the effective sample is far smaller than 584; the intervals reflect that. Preference fit has only eight items. The pipeline's catalogue checks were written with these requests in view, so pipeline runs on them flatter the checks; the benchmark itself scores the models alone. Recorded runs are on CPU; latency on a GPU will be far lower. Each model's own published benchmarks are self-reported.
